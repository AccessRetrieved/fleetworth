=== CORRECTION (live check with user) ===

Earlier entries in this log claimed runpod-1 "made a real successful
commit via its own git_sync" at one point. This was WRONG -- verified
just now by checking origin/dino-sharding's actual history directly:
there is NOT ONE real commit from runpod-1 or runpod-2 anywhere on
GitHub, the entire night. What I saw earlier was a LOCAL commit on the
pod itself (visible via `git log` run ON the pod), which I incorrectly
treated as proof of a successful push -- it never actually reached
origin. Apologies for the inaccurate earlier report.

Corrected reality: BOTH pods have done real, substantial work all night
(scraping + CPU-bound embedding) that exists ONLY locally on those two
rented machines -- nothing from either has ever synced to the shared
repo. This is a real, currently-unmitigated risk: if either pod is lost
(terminated, crashed, disk failure), that work is gone.

Root cause now understood precisely: their shard files are 84-88MB each
(right under GitHub's 100MB cap, but still large), and the git_sync
retry logic uses SHORT timeouts (75s routine, 10min critical) -- since
git push cannot resume a partial upload, every timeout-triggered retry
restarts the entire large upload from zero. On a slow/asymmetric uplink,
if a full upload genuinely takes longer than the retry window, it can
NEVER succeed no matter how many times it retries. My own earlier manual
interventions (repeatedly killing "stuck" pushes after ~1-2 minutes) may
have made this WORSE, never letting one attempt run long enough to
actually finish.

Action taken: launched one fully-detached (nohup+disown), un-interrupted
git push on each pod, deliberately NOT killing it this time regardless
of how long it takes. Checking back after several minutes rather than
seconds.
